# Учебный журнал по часам — изменения frontend

Журнал больше не должен повторять расписание. Пользователь работает с колонками вида «дата + количество часов», а внутри отмечает посещаемость и оценку. Тема и комментарий остаются необязательными.

## 1. Что показывать в журнале

В заголовке каждой колонки:

- дата;
- количество часов;
- необязательная тема.

Не показывать и не запрашивать:

- время начала и окончания;
- вид занятия;
- номер пары;
- источник из расписания;
- обязательную привязку к записи расписания.

## 2. Создание колонки

```http
POST /lk/api/v1/journal/lessons
```

```json
{
  "group_id": 201,
  "subject_id": 101,
  "date": "2026-09-07",
  "hours": 4,
  "topic_id": null,
  "topic_text": "Практическая работа № 1",
  "comment": null,
  "type": "practice",
  "status": "planned"
}
```

`hours` обязательно для нового frontend и принимает целое значение от 1 до 24. Поле `type` пока передаётся как техническое значение `practice`, но пользователю не показывается. Поля `starts_at`, `ends_at` и `schedule_lesson_id` передавать не нужно. Тема может быть пустой.

В ответе и в `GET /journal` каждая колонка содержит:

```ts
type JournalLesson = {
  id: number;
  date: string;
  hours: number;
  topic_text: string;
  // остальные служебные поля остаются для обратной совместимости
};
```

При редактировании `PATCH /journal/lessons/{id}` можно передавать `hours` вместе с `version`.

## 3. Контрольные точки

Формирование КТ больше не принимает `hours_per_lesson`:

```json
{
  "group_id": 201,
  "subject_id": 101,
  "academic_year": 2026,
  "semester": "autumn",
  "total_practical_hours": 68,
  "study_component": "discipline"
}
```

Backend делит семестровые часы на три накопительных порога. Для 68 часов это 23, 46 и 68 часов. КТ автоматически связывается с первой датой журнала, на которой сумма часов достигает соответствующего порога.

В объекте КТ добавлено поле:

```ts
planned_hours: number | null;
```

На frontend вместо «№ занятия» и «часов в занятии» показывать:

- рассчитанный порог накопленных часов;
- автоматически найденную дату журнала.

Порог и дата не требуют ручного ввода: backend пересчитывает их при формировании КТ. В настройках КТ пользователю достаточно управлять статусом.

`planned_lesson_number` остаётся в API только для обратной совместимости и не должен быть основной пользовательской настройкой.

## 4. Посещаемость

Автоматическая посещаемость рассчитывается пропорционально часам до соответствующей КТ. В score доступны новые понятные поля:

```ts
eligible_hours?: number;
attended_hours?: number;
```

Старые `eligible_lessons` и `attended_lessons` временно остаются как совместимые aliases и также содержат часы. Новому frontend следует использовать поля с суффиксом `_hours`.

## 5. Связь с расписанием

Для основного сценария связи нет: журнал создаётся и заполняется независимо. Расписание не должно автоматически добавлять, удалять или накладывать колонки журнала. Служебные поля `schedule_lesson_id`, `starts_at`, `ends_at` и `source` сохранены только для обратной совместимости со старыми клиентами и данными.

## 6. Выгрузка Excel

```http
GET /lk/api/v1/journal/export?group_id=201&subject_id=101&date_from=2026-09-01&date_to=2026-12-31
```

Запрос требует permission `journal.read` и того же назначения на пару «группа — дисциплина — учебный год — семестр», что и просмотр журнала.

Ответ имеет MIME type:

```text
application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
```

Frontend должен запрашивать ответ как `blob`, брать имя файла из `Content-Disposition` и запускать скачивание. Кнопка «Excel» показывается после выбора группы и дисциплины.

Файл содержит:

- лист «Учебный журнал»: студенты, даты и часы, посещаемость, оценки, пропущенные часы и средняя числовая оценка;
- лист «Даты и темы»: дата, часы, необязательная тема и комментарий.

Удалённые колонки журнала (`status = cancelled`) в файл не включаются. Данные расписания в выгрузку не добавляются.
