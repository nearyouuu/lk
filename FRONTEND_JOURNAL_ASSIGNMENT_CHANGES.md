# Электронный журнал — обязательные изменения frontend

Документ описывает изменения после перехода на общий журнал группы по дисциплине. Главная идея: преподаватель назначается на журнал один раз, а не отдельно на занятие или контрольную точку.

## 1. Новая модель доступа

Источник доступа:

```text
teacher_id + group_id + subject_id + academic_year + semester
```

Назначения управляются через:

```http
GET    /lk/api/v1/admin/journal/assignments
POST   /lk/api/v1/admin/journal/assignments
DELETE /lk/api/v1/admin/journal/assignments/{assignment_id}
```

Одно назначение даёт преподавателю доступ к:

- общему журналу группы по дисциплине;
- занятиям всех назначенных на журнал преподавателей;
- посещаемости и оценкам;
- контрольным точкам;
- рейтинговой ведомости.

Если назначено несколько преподавателей, frontend не должен создавать для каждого отдельный журнал или отдельные КТ.

## 2. Каталог журнала

```http
GET /lk/api/v1/journal/catalog?academic_year=2026&semester=autumn
```

Каталог теперь содержит только активные назначения. Расписание больше не добавляет группы и дисциплины в каталог автоматически.

При deployment текущие связи из существующего расписания будут один раз перенесены backend-миграцией в явные назначения. Поэтому они появятся в административной таблице `journal_assignments`; после миграции изменения расписания больше не создают и не удаляют доступ автоматически.

Frontend должен:

1. Загружать доступные пары только из `/journal/catalog`.
2. Не объединять каталог с данными расписания.
3. Если нужной пары нет, направлять администратора к созданию назначения.

## 3. Общие колонки журнала нескольких преподавателей

`GET /journal` возвращает все колонки выбранной группы и дисциплины независимо от `teacher_id` записи.

Поле занятия:

```json
{
  "teacher_id": 42
}
```

означает проводящего преподавателя и используется только для отображения. Нельзя фильтровать по нему доступ или скрывать занятие от другого назначенного преподавателя.

При создании занятия обычным преподавателем `teacher_id` передавать не нужно:

```json
{
  "group_id": 201,
  "subject_id": 101,
  "date": "2026-09-07",
  "hours": 4,
  "type": "practice",
  "topic_text": "Практическая работа № 1"
}
```

При создании от имени администратора:

- если назначен один преподаватель, `teacher_id` можно не передавать;
- если назначено несколько, нужно показать выбор преподавателя и передать `teacher_id`;
- выбрать преподавателя без активного назначения нельзя.

Новые ошибки формы:

| Код | Отображение |
|---|---|
| `JOURNAL_ASSIGNMENT_REQUIRED` | Сначала назначьте преподавателя на журнал |
| `JOURNAL_TEACHER_REQUIRED` | Выберите проводящего преподавателя |
| `JOURNAL_TEACHER_NOT_ASSIGNED` | Преподаватель не назначен на выбранный журнал |

## 4. Контрольные точки

Из всех TypeScript-типов, форм и таблиц КТ нужно удалить `teacher_id`.

Запрос формирования КТ:

```json
{
  "group_id": 201,
  "subject_id": 101,
  "academic_year": 2026,
  "semester": "autumn",
  "total_practical_hours": 68,
  "study_component": "discipline"
}
```

Необходимо удалить:

- выбор преподавателя в форме формирования КТ;
- передачу `teacher_id` в `control-points:generate`;
- колонку преподавателя в локальной модели КТ;
- фильтрацию КТ по преподавателю.

КТ общие для комбинации:

```text
group_id + subject_id + academic_year + semester
```

## 5. Разделение журнала и расписания

Основной журнал полностью независим от расписания: frontend создаёт только дату, часы и необязательную тему. Поля времени, типа и связи с расписанием в пользовательском интерфейсе не нужны. Подробный актуальный контракт описан в `FRONTEND_JOURNAL_HOURS_CHANGES.md`.

Frontend не должен накладывать `schedule_lessons` поверх `journal_lessons` и объединять два массива по дате и времени.

Основная таблица строится только из ответа:

```http
GET /lk/api/v1/journal
```

У занятия журнала теперь есть признак происхождения:

```ts
type JournalLessonSource = "manual" | "schedule";

type JournalLesson = {
  id: number;
  schedule_lesson_id: number | null;
  source: JournalLessonSource;
};
```

Расписание можно показывать отдельно как список предложений «Добавить в журнал». После добавления запись становится обычным `journal_lesson` и отображается только из ответа журнала.

Правила `schedule_lesson_id`:

- `null` — занятие создано вручную;
- число — занятие связано с расписанием;
- группа и дисциплина должны совпадать;
- одну запись расписания нельзя добавить дважды;
- связь с расписанием не выдаёт преподавателю доступ к журналу.

Ошибки:

| Код | Действие frontend |
|---|---|
| `JOURNAL_SCHEDULE_LESSON_NOT_FOUND` | Удалить устаревшее предложение расписания |
| `JOURNAL_SCHEDULE_LESSON_MISMATCH` | Обновить данные выбранной группы и дисциплины |
| `JOURNAL_SCHEDULE_LESSON_ALREADY_IMPORTED` | Закрыть форму и обновить журнал |

## 6. Что удалить из frontend

- Логику «есть занятие в расписании — значит преподаватель имеет доступ».
- Фильтрацию занятий общего журнала по `lesson.teacher_id`.
- `teacher_id` в моделях и формах контрольных точек.
- Автоматическое объединение расписания и журнала на клиенте.
- Отдельные КТ для каждого преподавателя.

## 7. Порядок обновления запросов

После создания или удаления назначения обновить:

```ts
["journalCatalog", academicYear, semester]
["journalAssignments", academicYear, semester]
```

После добавления занятия из расписания обновить:

```ts
["journal", groupId, subjectId, dateFrom, dateTo]
["scheduleSuggestions", groupId, subjectId, dateFrom, dateTo]
```

После изменения занятия, посещаемости или оценки обновить общий журнал и рейтинговую ведомость без фильтра по преподавателю.
